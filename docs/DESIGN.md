# 実装方針

## 1. レイヤー構成

```
┌──────────── #stage（CSS 背景 = #D9DCD6）────────────┐
│  canvas#paper    … 画像キャンバスの下地（§7）。通常は空  │
│  canvas#ink      … 確定済みの絵。背景は透明            │
│  canvas#overlay  … 未確定の貼り付け画像・ハンドル・     │
│                    ブラシカーソル。ポインタ入力もここで受ける │
│  DOM             … ヒント・トースト（書き出しには入らない） │
└──────────────────────────────────────────────────────┘
```

- **インクレイヤーは透明**にして、グレーの背景は CSS で敷いています。
  消しゴムは `globalCompositeOperation = "destination-out"`（＝透明に戻す）で実装しているので、
  確定済みの貼り付け画像もペンの線も同じように消せます。
- **オーバーレイを分けている**のが「未確定画像」を実現するポイントです。
  未確定の間はインクレイヤーに一切触れず、オーバーレイに毎フレーム描き直すだけなので、
  何度動かしても画質が劣化せず、キャンセルも「オーバーレイを消すだけ」で済みます。
- HiDPI 対応: `ResizeObserver` の `devicePixelContentBoxSize` で実ピクセル数を取り、
  キャンバスのバッファを実ピクセル、座標系を CSS px（`setTransform(dpr, …)`）にしています。
  Windows の表示スケール 125% でも線がボケず、書き出し PNG も画面と 1:1 になります。

## 2. ペーストした画像を確定させるまでの UI

### 状態遷移

```
             Ctrl+V / D&D
  [通常] ─────────────────────▶ [未確定 floating]
    ▲                              │  ├ 内側ドラッグ … 移動
    │                              │  ├ 角ドラッグ  … 拡縮（反対側の角を固定）
    │ Enter / 外側クリック          │  ├ ◯ドラッグ   … 回転
    │ / Ctrl+C / 次のペースト       │  └ ホイール・矢印 … 拡縮・微移動
    │ → board.addImage()（焼き付け）│
    ├──────────────────────────────┘
    │ Esc / Delete / Ctrl+Z → 破棄（履歴には何も残らない）
```

### データ

```ts
interface ImageTransform { cx; cy; w; h; rotation }   // 中心・表示サイズ・回転（CSS px / rad）
class FloatingImage { bitmap: ImageBitmap; t: ImageTransform }
```

変形は「中心 + サイズ + 角度」の 5 値だけで表します。行列を積み重ねないので誤差が溜まりません。

### 当たり判定（`floating.ts`）

ポインタ座標を**画像のローカル座標系**（中心が原点・回転を打ち消した座標）に変換してから判定します。
これで回転していても「軸に平行な矩形」との比較で済みます。

```
local = rotate(p - center, -rotation)
回転ハンドル: |local - (0, -h/2 - 28)| <= 12
角          : |local.x ∓ w/2| <= 10 && |local.y ∓ h/2| <= 10
内側        : |local.x| <= w/2 && |local.y| <= h/2
```

ハンドルの大きさは画像の拡大率に関係なく画面上で一定（CSS px 固定）です。
角のカーソル（`nwse-resize` など）も回転角に合わせて 45° 単位で切り替えています。

### ドラッグ中の計算

ドラッグは常に「**開始時点の transform + 開始時点のポインタ位置**」からの差分で計算します（`DragStart`）。
途中の値を積み重ねないので、Shift を押したり離したりしても破綻しません。

- **拡縮**: 反対側の角 F を固定点とし、F → ポインタのベクトルを画像のローカル軸（u, v）に射影。
  縦横比固定時は対角線方向への射影 `t = (dx·w + dy·h) / (w² + h²)` を倍率にすると、手の動きに自然に追従します。
  新しい中心は `F + (w'/2)·u + (h'/2)·v` で求めるので、回転していても固定点がずれません。
- **回転**: 中心から見た「開始時のポインタ角度」と「現在の角度」の差を足すだけ。Shift で 15° にスナップ。

### 確定

`Enter` / 外側クリック / `Ctrl+C` / 次のペーストで `board.addImage(bitmap, transform)` を呼び、
インクレイヤーに `translate → rotate → drawImage` で焼き付けます。
履歴には `{ kind: "image", bitmap, transform }` が 1 件積まれ、以降は動かせません（Undo は可能）。

外側クリックは「確定するだけ」で、そのクリックでは線を引きません（`gesture = "swallow"`）。
また、ツールバーのボタンは `mousedown` で `preventDefault` してフォーカスを奪わないようにしています。
そうしないと、直前に押した「すべて消去」ボタンにフォーカスが残り、確定のつもりの `Enter` でもう一度消去が走ってしまいます。

### 初期配置

画像 1px = 画面の実ピクセル 1px（`bitmap.width / devicePixelRatio`）で中央に置き、
キャンバスの 90% に収まらなければ縮小します。スクショを貼ってもボケず、巨大画像でも画面からはみ出しません。

### 画像の取り込み経路

| 入力 | 取得方法 |
| --- | --- |
| スクショ・ブラウザの「画像をコピー」 | `paste` イベントの `clipboardData.items`（`image/*`） |
| エクスプローラーでコピーした画像ファイル | `paste` イベントの `clipboardData.files`（拡張子で判定） |
| 上記で取れなかった場合の保険 | Rust の `read_clipboard_image`（CF_HDROP → ビットマップの順に探す） |
| エクスプローラーからのドラッグ＆ドロップ | `drop` イベント（`tauri.conf.json` で `dragDropEnabled: false` にして HTML5 D&D を有効化） |

`clipboardData` はハンドラを抜けると読めなくなるので、Blob の取り出しだけ同期で行い、デコード（`createImageBitmap`）は非同期にしています。
`Ctrl+V` を押しても `paste` イベントが来なかった場合に備え、150ms 後に Rust 側へ読みに行くフォールバックもあります。

## 3. 投げ縄選択

ペンでなぞるように囲んだ部分を切り取り、貼り付け画像と同じハンドルで移動・拡縮・回転できます。

```
[通常] ──投げ縄でなぞる──▶ overlay にパスを薄く塗って表示（始点まで自動で閉じる）
   │
   └─ 離す ─▶ board.extractRegion(path)   パスで clip して実ピクセルを切り出し ImageBitmap に
              board.setPendingCut(path)    元の場所に穴を空ける（表示だけ。履歴には入れない）
              FloatingImage.fromSelection  ← 以降は貼り付け画像と同じ UI
                 │
                 ├ Enter / 外側クリック → board.commitSelection(path, bitmap, transform)
                 │                         （動かしていなければ何も記録せず元に戻す）
                 ├ Delete              → board.commitSelection(path, null, null)（削除）
                 └ Esc / Ctrl+Z        → board.setPendingCut(null)（元に戻す）
```

- 履歴には `{ kind: "selection", path, bitmap, transform }` を **1 件だけ**積みます。
  再生時は「path の内側を destination-out で消す → bitmap を transform で描く」なので、
  `Ctrl+Z` 1 回で切り取りと移動がまとめて元に戻ります。
- 切り出しは実ピクセル単位の矩形に揃えているので、動かしただけなら画質は変わりません。
- 持ち上げている間の「穴」は `pendingCut` として Board が覚えていて、ウィンドウのリサイズで描き直しても消えません。
- パスの塗りは `nonzero` なので、8 の字のように交差した投げ縄でも囲まれた部分はすべて選択されます。
- 何も描かれていない範囲を囲んだ場合は持ち上げず、トーストで知らせます。

## 4. クリップボードへの PNG エクスポート

```
board.exportCanvas()           背景 #D9DCD6 で塗った新規キャンバスに、インクレイヤーを重ねる
        │                      （実ピクセル解像度。未確定画像は先に確定させる）
        │                      画像キャンバスでは「下地の画像 + 書き込み」を画像と同じ大きさで（§7）
        ▼
canvas.toBlob("image/png")     ブラウザ側で PNG エンコード（非同期で UI を止めない）
        │
        ├─ Tauri 上 ──▶ invoke("copy_png_to_clipboard", Uint8Array)
        │                  │  Uint8Array は JSON を経由せず raw バイト列のまま IPC で渡る
        │                  ▼
        │              Rust: PNG → RGBA にデコード → arboard.set_image()
        │                  → Windows のクリップボードに "PNG" と CF_DIBV5 を登録
        │
        └─ 失敗時 / ブラウザ ──▶ navigator.clipboard.write([new ClipboardItem({ "image/png": blobPromise })])
```

- **ネイティブ（Rust）を優先する理由**: Web の Async Clipboard API は「ドキュメントにフォーカスがある」
  「ユーザー操作の直後」などの条件に左右されます。Rust 側はその制約がなく、書き込む形式も制御できます。
  `PNG` 形式（Chromium 系・Office などが優先して読む）と `CF_DIBV5`（ペイントなど古いアプリ向け）の両方を置くので、貼り付け先を選びません。
- `ClipboardItem` には `Promise<Blob>` をそのまま渡しています。エンコード完了を `await` してから渡すと、
  ブラウザによっては「ユーザー操作の直後」扱いが切れて拒否されるためです。
- ファイル保存機能は持たないので、WebView の右クリックメニュー（「名前を付けて画像を保存」を含む）も無効化しています。

## 5. 履歴（Undo / Redo）

ピクセルのスナップショットではなく、**描画コマンドの配列**で持っています。

```ts
type Command =
  | { kind: "stroke"; tool; color; size; points: number[] }
  | { kind: "image"; bitmap; transform }
  | { kind: "clear"; page: ImageBitmap | null }   // page があれば画像キャンバスの始まり（§7）
  | { kind: "selection"; path; bitmap | null; transform | null };
```

- WQHD のスナップショットは 1 枚 14MB を超えるので、コマンド方式の方が圧倒的に軽い
- ウィンドウサイズや表示スケールが変わっても、コマンドを再生すれば劣化なく描き直せる
  （ウィンドウを小さくしてはみ出した部分も、広げれば戻ってくる）

毎回すべてを再生すると重くなるので、**24 手前の状態をオフスクリーンの base キャンバスにキャッシュ**し、
Undo 時は `base + 直近のコマンド` だけを再生します。Redo は今の画面に 1 コマンド重ねるだけです。
base より前まで戻ったときだけ作り直します（直近の「全消去」より前は再生をスキップ）。

線は中点を結ぶ二次ベジェで滑らかにしています。描画中は 1 区間ずつ、再生時は 1 本のパスとして同じ形を描きます。
`getCoalescedEvents()` で高ポーリングレートのマウスやペンタブの中間点も拾っています。

## 6. タイトルバー

OS のタイトルバーには画像を置けないので、`tauri.conf.json` で `decorations: false` にして HTML で描いています
（左端にアイコンとロゴ画像、右端に 最小化 / 最大化 / 閉じる）。

- **移動・最大化**: バーに `data-tauri-drag-region="deep"` を付けているので、ボタン以外のどこを掴んでもドラッグで移動、
  ダブルクリックで最大化 / 元に戻すになります（Tauri 側の処理。画面端へのスナップも OS のものがそのまま効きます）。
- **リサイズ**: 枠なしウィンドウでも Tauri（tao）が縁のヒットテストをしてくれるので、OS と同じように縁をつまんで変えられます。
- **ボタン**: `titlebar.ts` で `getCurrentWindow().minimize()` などを呼びます。許可は `capabilities/default.json` に
  `core:window:allow-start-dragging` / `allow-minimize` / `allow-toggle-maximize` / `allow-close` を追加しています。
  グリフは Windows 標準と同じ Segoe Fluent Icons（Windows 10 は Segoe MDL2 Assets）で、閉じるのホバーは標準の赤です。
  最大化状態は `onResized` のたびに `isMaximized()` で確認してアイコンを切り替えます。
- **非アクティブ表示**: `onFocusChanged` でほかのウィンドウを操作している間はロゴとボタンを薄くします。
- ロゴはドット絵なので、`image-rendering: pixelated` で拡大時もにじませません。
  左端のアイコンは `npm run icons` が 20px 用に描いたもの（高 DPI 用に 40px も `srcset` で用意）です（§8）。
  Vite が 4KB 未満の画像を data URI としてインライン化するので、CSP の `img-src data:` で表示できます。
- ブラウザで開いたとき（`npm run dev`）はウィンドウを操作できないので、ボタンだけ隠しています。

## 7. 画像キャンバス（クリップボードから開く）

スクショを撮って「クリップボードから開く」（`Ctrl+Shift+V`）を押すと、その画像がそのままキャンバスになります。
書き出しは画像と同じ大きさ・解像度で、周りのグレーは入りません。

### 座標系

```
CSS px（ポインタ・オーバーレイ・未確定画像）
   │  board.toDoc() / board.toCss()   … View: css = doc * s + o
   ▼
doc 座標（履歴のコマンドが持つ座標）
   │  ink / base / paper の setTransform(a, 0, 0, d, e, f)
   ▼
実ピクセル（キャンバスのバッファ）
```

- 通常のキャンバスでは、最初は doc 座標 = CSS px（`s = 1, o = 0`）です。拡大・縮小や表示の移動で `s` と `o` が変わります（10 章）。
- 画像キャンバスでは doc 座標 = 画像のピクセルです。開いた直後は、画面に収まるなら「画像 1px = 実ピクセル 1px」で中央に置き
  （描くときの位置は実ピクセルに揃えるので、スクショがにじまない）、収まらなければ周りに 16px 残して縮小表示します。
  そのあとは、ウィンドウの大きさが変わっても配置は変えません（描いたものが画面上で動かないように。10 章）。
- ペンの太さは画面上の見た目（CSS px）で選ぶので、doc 座標では `太さ / s` にして記録します（縮小表示でも見たままの太さで書き出される）。
- 未確定画像（`FloatingImage`）は CSS px のまま扱い、確定するときに doc 座標へ変換します。
  未確定のままウィンドウの大きさが変わったときは `remap()` で一緒に動かし、キャンバスに対して同じ位置・大きさに留めます。
- `Ctrl+V` で重ねる画像は「その画像の 1px = doc の 1px」で置きます（スクショの上にスクショを貼っても縮尺が揃う）。

### 下地（紙）と書き込みを分ける

```
canvas#paper … 下地の画像（＋紙の色・影）。消しゴムは届かない
canvas#ink   … 書き込み。画像の範囲で clip しているので、はみ出した線は表示も書き出しもされない
```

画像をインクレイヤーに焼いてしまうと、消しゴムでスクショまで消えてしまいます。
通常のキャンバスの「グレーの紙」と同じ扱いにして、消しゴムは書き込みだけを透明に戻すようにしています。
投げ縄で動かせるのも書き込みだけです。

### 解像度を落とさない

縮小表示中の画面（実ピクセル）は画像より解像度が低いので、ここから切り出したり書き出したりすると画質が落ちます。
そこで画像キャンバスでは、**書き出しと投げ縄の切り出しのときだけ、コマンドを画像と同じ解像度のオフスクリーンキャンバスに描き直して**使います
（`renderPageInk()`）。線はベクターのコマンドなので、元の解像度でくっきり描き直せます。

### 履歴

画像キャンバスの始まりは `{ kind: "clear", page: ImageBitmap }` として履歴に積みます。
「全消去 + 下地の差し替え」なので、`Ctrl+Z` 1 回で開く前のキャンバス（とそこに描いていたもの）に戻ります。
ゴミ箱は `{ kind: "clear", page: null }` で、画像ごと消して通常のキャンバスに戻ります。

Undo / Redo で `clear` をまたいで下地が変わったときは、doc 座標の意味が変わるので配置を決め直して全部描き直します（`followPage()`）。
base キャッシュも描き直すので、Undo の速さはこれまでと変わりません。

### クリップボードの読み取り

ボタンや `Ctrl+Shift+V` では paste イベントが来ないので、Rust の `read_clipboard_image` で読みます
（エクスプローラーでコピーした画像ファイル → `PNG` 形式 → `CF_DIBV5` の順）。
`Ctrl+Shift+V` は既定で「書式なしで貼り付け」の paste イベントが起きるので、keydown で止めています。

WebView へ渡すために PNG に詰め直すとき、既定の Adaptive フィルタ（行ごとに 5 種類試す）は重いので、
`CompressionType::Fast` + `FilterType::Up` にしています（同じ PC 内で渡すだけなので圧縮率は関係ない）。
2560×1440 のスクショで、読み取りは約 70ms → 25ms になりました。

## 8. 画面から取得

Snipping Tool の「四角形」のように、画面の一部を撮ってそのまま画像キャンバスにします。
撮るのは**ボタンを押した瞬間の 1 回だけ**で、範囲はその静止画から選びます（選んでいる間に画面が動いても関係ない）。

```
main.ts  captureScreenAsPage()
   └─ invoke("capture_screen_region")  ──────────────── Rust（screen_capture.rs）
                                          1. メインウィンドウを隠す（DWM の表示アニメーションも止める）→ 220ms 待つ
                                          2. 仮想スクリーン（全モニター）を GDI の BitBlt で 1 回だけ撮る
                                          3. 全モニターを覆う枠なし・最前面のウィンドウ（capture.html）を非表示で作る
             capture.ts ◀─ get_screen_capture ──┘   （静止画 + 案内を出すモニターの位置）
               静止画を描き終えたら show_capture_overlay → 表示・フォーカス
               ドラッグで四角形 → finish_screen_capture(x, y, w, h)
               Esc / 右クリック → cancel_screen_capture
                                          4. 静止画から切り抜く → 範囲選択のウィンドウを閉じて、メインウィンドウを戻す
   ◀─ [width][height][RGBA...]（キャンセルなら空）
   └─ openAsPage(bitmap) … 「クリップボードから開く」と同じ画像キャンバスになる（Ctrl+Z で戻せる）
```

### 撮影（Rust）

- 全モニターをまとめた仮想スクリーン（`SM_XVIRTUALSCREEN` ほか）を `BitBlt(SRCCOPY | CAPTUREBLT)` で撮ります。
  Tauri のプロセスは Per-Monitor DPI Aware v2 なので、座標も画素も物理ピクセルです（表示スケール 125% でもボケない）。
  `CAPTUREBLT` は半透明のウィンドウも写すためのフラグです。
- 自分のウィンドウが写り込まないよう、撮る前に隠します。Windows のウィンドウには消えるときのアニメーションがあるので、
  `DWMWA_TRANSITIONS_FORCEDISABLED` で止めてから隠し、念のため 220ms 待ってから撮ります（戻したあと 500ms で元に戻す）。
- 画像のやり取りは PNG にせず、ヘッダー付きの生の RGBA を raw の IPC で渡します。
  WQHD 3 枚（7680×1440）でも 44MB の memcpy で済み、PNG のエンコード / デコードを待たずに済みます。

### 範囲選択の画面（capture.html）

- 仮想スクリーンと同じ位置・大きさ（物理ピクセル）の枠なし・最前面・タスクバーに出ないウィンドウです。
  静止画を描き終えてから表示するので、白い画面が一瞬見えることはありません。DPI の違うモニターをまたぐと表示した瞬間に大きさが変わることがあるので、表示の前後で位置と大きさを合わせ直しています。
- キャンバスは静止画と同じ解像度にして CSS で全面に広げ、ポインタ位置は「キャンバスの幅 ÷ 表示幅」で静止画のピクセルに直します。
  ウィンドウの DPI に関係なく、選んだ範囲は静止画のピクセル単位で正確になります。
- 下のキャンバスに「暗くした静止画」を 1 回だけ描き、上のキャンバスに「選んでいる部分（元の明るさ）+ 枠 + 大きさの表示」を毎フレーム描きます。
  枠は選んだ範囲の外側に描くので、撮る中身にはかかりません。
- 案内は、ボタンを押したときにメインウィンドウがあったモニターの上端中央に出します（マルチモニターで継ぎ目に出ないように）。

### 失敗しても戻れるように

- 範囲選択のウィンドウが Alt+F4 などで閉じられたら、キャンセル扱いにします（`WindowEvent::Destroyed`）。
- 範囲選択の画面が 8 秒以内に表示されなければ、諦めてエラーにします。メインウィンドウが隠れたままになるのを防ぐためです。
- どの終わり方でも、最後に範囲選択のウィンドウを閉じてメインウィンドウを戻してから結果を返します。
- 同時に 2 回は動かしません（2 回目は「すでに画面の取得中です」）。

## 9. macOS 対応

Tauri は Mac でもそのまま動くので、違いは「設定の重ね書き」と「見た目・キー操作の差」だけにしています。

### 設定（`src-tauri/tauri.macos.conf.json`）

Tauri は Mac でビルドするとき、`tauri.conf.json` に `tauri.macos.conf.json` を JSON Merge Patch で重ねます（配列は丸ごと置き換え）。

- **ウィンドウ**: Windows は `decorations: false` で自前のタイトルバーを描いていますが、Mac で同じことをすると信号機ボタン（閉じる・しまう・フルスクリーン）が消えてしまいます。
  Mac では `decorations: true` + `titleBarStyle: "Overlay"` + `hiddenTitle: true` にして、OS のタイトルバーを透明にして WebView の上に重ねます。
  自前のタイトルバー（ロゴとドラッグ領域）はそのまま使い、左側を信号機ボタンの分（78px）だけ空けます。
- **バンドル**: `targets: ["app", "dmg"]`。`minimumSystemVersion` は 12.0。
- **署名**: `signingIdentity: "-"`（アドホック署名）。Apple シリコンの Mac は署名のないアプリを起動できず、
  署名が壊れていると「壊れているため開けません」になるので、最低限アドホック署名はしておきます。
  公証（Notarization）はしていないので、初回は「このまま開く」の操作が必要です（README 参照）。

### 画面とキー操作（`src/platform.ts`）

- WKWebView の UA（`Macintosh`）で Mac を判定し、`<html data-platform="mac">` を付けて CSS を切り替えます。
  信号機ボタンの余白は、アプリ版のときだけ（`data-native="true"`）空けます。
- キー操作はもともと `ctrlKey || metaKey` で受けているので、`⌘+Z` などはそのまま動きます。
  表示だけ、ツールチップ・`<kbd>`・トーストの `Ctrl` を `⌘` に書き換えます。
- WebView の既定ショートカットを止めるリストから、Mac では `⌘+W`（ウィンドウを閉じる）と `⌘+H`（隠す）を外しています。
  Mac ではメニューの標準操作なので、止めると不便です。WKWebView はキー操作をまずページに渡し、ページが止めなかったものだけメニューに回します。
- 「画面から取得」は Windows の GDI で撮っているので、Mac ではボタンを出しません。
  Mac で同じ「押した瞬間の静止画から選ぶ」をやるには、ScreenCaptureKit での撮影、画面収録の許可（TCC）の扱い、ディスプレイごとの範囲選択ウィンドウが必要になるので、別に作ります。

### WebKit との違い

Mac の WebView は Chromium ではなく WebKit（Safari と同じエンジン）です。今のコードで差が出るところは、どれも最初から代わりの処理を用意してあります。

| 機能 | WebKit | 対応 |
| --- | --- | --- |
| `ResizeObserver` の `device-pixel-content-box` | 非対応（例外になる） | 例外を捕まえて通常の `observe` にし、`CSS px × devicePixelRatio` で実ピクセルを求める |
| `PointerEvent.getCoalescedEvents()` | 古い Safari は非対応 | `?.()` で、無ければその 1 点だけ使う |
| `OffscreenCanvas` の 2D | Safari 16.4 以降 | macOS / Safari を最新にしてもらう（README） |

Mac 対応のときに、WebKitGTK（Linux 版の WebKit）の MiniBrowser を WebDriver で動かして、
描画・Undo・貼り付けと変形・投げ縄・PNG 書き出し・画像キャンバスが WebKit でも JS エラーなく動くことを確かめました（このテストはリポジトリには入れていません）。

### ビルドと配布

- **macOS app** ワークフロー（push ごと）と **Release** ワークフローの macOS ジョブで、`macos-latest` 上で
  `npm run tauri build -- --target universal-apple-darwin` を実行し、Intel / Apple シリコン両対応の `.dmg` を作ります。
- Release は Windows と macOS を matrix で並行してビルドします（`fail-fast: false` なので片方が失敗しても、もう片方は添付されます）。
  2 つのジョブが同時にリリースを作ろうとすることがあるので、作るのに失敗してもリリースがあればそのまま添付に進みます。

## 10. 拡大・縮小、表示の移動、ウィンドウのリサイズ

表示の配置は `View`（`css = doc * s + o`）1 つで表し、Board が状態として持ちます。
これまでは「ウィンドウの大きさから毎回計算するもの」でしたが、拡大・縮小や移動を覚えておくために状態にしました。

| 操作 | View の変化 |
| --- | --- |
| 開いたとき / 下地が変わったとき / `Ctrl+0` | 最初の配置（`homeView()`: 通常は等倍・左上、画像キャンバスは中央に収める） |
| `Ctrl` + ホイール / ピンチ / `Ctrl+=` `Ctrl+-` | カーソル（キーボードはステージ中央）p を中心に `k` 倍: `s *= k`、`o = p - (p - o) * k` |
| ホイール / `Space` + ドラッグ / 中ボタンドラッグ | `o += 移動量` |
| ウィンドウのサイズ変更 | ステージが画面上で動いた分だけ `o -= 移動量`（下で説明） |

- 倍率の範囲は 10%〜1600%（画像キャンバスで最初から 10% より小さく表示している場合は、その倍率まで縮小できる）。
  倍率は、通常のキャンバスは CSS px、画像キャンバスは「画像 1px = 実ピクセル 1px」を 100% とします。
- `View` 自体は丸めずに持ち、描くときの変換（`toDevice`）だけ実ピクセルに丸めます。
  `View` を丸めて書き戻すと、細かい移動を繰り返したときに誤差が積み重なって、カーソルと絵がずれていくためです。
- 表示を変えるたびに全コマンドを描き直すので、ホイールなどの細かい入力は 1 フレームにまとめてから反映します。
- 未確定の画像は CSS px で持っているので、表示が変わったら `remap()` で一緒に動かします（doc 座標での位置は変わらない）。
- 画像キャンバスの下地は、縮小表示ではなめらかに、拡大表示ではドットがはっきり見えるように描きます（スクショの文字がぼやけない）。
- Mac（WebKit）のトラックパッドのピンチは wheel ではなく `gesturechange` で届くので、それも拡大・縮小に使います。

### 書き出し

- 通常のキャンバス: 表示中のキャンバスをそのまま（見えているとおり。ウィンドウと同じ大きさ）。
  拡大中は見えている部分、縮小中は見えている全体になります。書き出しの大きさがウィンドウより大きくならないので、
  縮小しすぎて巨大な画像を作ってしまうこともありません。
- 画像キャンバス: これまで通り、倍率に関係なく画像と同じ大きさ・解像度。

### リサイズしても絵を動かさない

キャンバスの原点はステージの左上なので、ウィンドウの左辺や上辺をつかんで縮めると、絵がウィンドウと一緒に動いて見えます
（右辺や下辺なら原点が動かないので、絵も動かない）。そこで、ステージの左上が画面上でどれだけ動いたかを測って、
その分だけ表示を逆にずらします。

- ステージの画面上の位置 = `window.screenX/Y` + `stage.getBoundingClientRect()`。
  WebView2 は、親ウィンドウが動いたことを wry が `NotifyParentWindowPositionChanged()` で伝えているので、`screenX` が追従します。
  ツールバーの折り返しでステージが下にずれたときも、同じ仕組みで絵が止まります。
- サイズが変わったとき（`ResizeObserver`）に、前回からの位置の差だけ表示をずらします。
- ウィンドウの位置の通知がサイズより遅れて届くこともあるので、サイズが変わってから 200ms の間は毎フレーム位置を確かめて、
  動いていたらその分もずらします。
- ウィンドウを動かしただけ（サイズは同じ）のときは、絵ごと動くのが自然なので、位置を覚え直すだけにします
  （Tauri の `onMoved`、ポインターの移動、フォーカスのたびに確認）。

## 11. バケツ（塗りつぶし）

```
見えている色（背景 + 下地の画像 + 書き込み を、書き込みと同じ解像度で合成）
   │ flood fill（クリックした所から、同じ色でつながっている範囲）
   ▼
マスク ─┬─ core   … 範囲そのもの。上から塗る
        └─ fringe … 外周 1px。今ある線の「下」に塗る
   │
   ▼
履歴 { kind: "fill", core, fringe, rect }
```

- 範囲は「見えている色」で決めます。背景や下地の画像の色の境目でも止まるので、スクショの枠の中なども塗れます。
  塗った色は書き込みのレイヤーに描くので、消しゴム・投げ縄・塗り直しの対象になり、下地の画像は変わりません。
- 範囲の判定はスキャンライン法の flood fill です。RGB それぞれの差が 48 以内なら同じ色とみなします（アンチエイリアスや JPEG のノイズを吸収）。
- **線とのすき間を残さない**: 線のフチはアンチエイリアスで背景と混ざった色になっていて、範囲に入らないことがあります。
  そのまま塗ると線との間に元の色が細く残るので、範囲の外周 1px（fringe）も塗ります。
  ただし fringe は `destination-over`（今ある書き込みの「下」）に描くので、線は上に残り、すき間だけが埋まります。
  範囲そのもの（core）は普通に上から塗るので、塗った所を別の色で塗り直すこともできます。
- 解像度: 通常のキャンバスは表示中のキャンバス（実ピクセル）、画像キャンバスは画像のピクセル。
  塗った結果は画像として持ち、`rect`（doc 座標）に置くので、拡大・縮小しても同じ場所に描かれます。
- 通常のキャンバスで塗れるのは見えている範囲までです（書き出しと同じ範囲）。
- クリックした所がすでに同じ色なら何もしません。

## 12. アプリアイコンの生成（`npm run icons`）

元の絵 `assets/soyokazeMemoIcon.png` は SoyokazeMemo で描いた手描きの絵（紙のグレーにスレートブルー 1 色）で、正方形ではありません。
`scripts/generate-icons.ps1` が、ここから各サイズのアイコンを直接描きます。

1. **線だけを抜き出す**: いちばん多い色を紙、紙から十分離れた色でいちばん多い色を線の色とし、
   各ピクセルを「紙 → 線の色」の軸に射影して線の濃さ（0〜1）にします。アンチエイリアスの縁も濃さとしてそのまま残ります。
2. **正方形のタイルに収める**: 紙と同じ色の角丸タイル（縁取りは紙の色を 15% 暗くしたもの）を描き、
   線がある範囲を縦横比を保ったまま中央に収めます。
3. **小さいサイズは線を太らせる**: 元の絵の線は約 7px なので、24px のアイコンにそのまま縮小すると 0.3px ほどになって消えかけます。
   距離変換（Felzenszwalb の方法）で「いちばん近い線までの距離」を求めておき、
   縮小後に線が 1.6px 以上残るぶんだけ元の絵の段階で線を太らせてから、面積平均で縮小します（大きいサイズは元の線のまま）。
4. **書き出し**: `icon.ico`（16〜256px の 10 サイズ）と主要な PNG、タイトルバー用の `assets/titlebar-icon*.png` はこの方法で描き、
   icns と Store 用のロゴは 1024px で描いたものから `tauri icon` に作らせます。

`tauri-build` は `tauri.conf.json` と `capabilities` の変更でしかビルドスクリプトを再実行しないので、
アイコンだけ差し替えると手元のビルドでは exe に埋め込み直されません。`build.rs` で `icons` フォルダも監視しています。
